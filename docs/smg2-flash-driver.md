## 1. 呼び出し連鎖 【掃引のエッジで確認済み】

矢印は**実際に確認した呼び出しエッジ**だけです。確認していないものは矢印にしていません。

```
FUN_00ad30   ASC0 受信割込み。DS2 フレームを組み立てるだけで、何も呼びません
             （掃引のエッジ: 出ていく呼び出し 0 本）
             0x32 宛て検査 → XOR 検算 → 完了で FD00 bit1

FUN_0027c4   ディスパッチャ。1C2A と 2212 の両方を呼ぶ唯一の関数
   ├─▶ FUN_001c2a   SEED/KEY (サービス 0x90)。"BMW" → 鍵計算 → E023 = 0x02/0x20（解錠）
   └─▶ FUN_002212   サービス 0x07。E05F がサブ機能 0x06=消去 / 0x02=書込 / 0x0F=終了
          │
          ▼ FUN_00137e  番地検証 → 領域コード LAB_0006a6_1（1 または 2、不正は 0）
          ▼ FUN_000ffe  領域で分岐
          ▼ FUN_0014b4  セクタ消去ループ
          ▼ FUN_000af8  → FUN_00097e  コピーして RAM で実行
```

`FUN_00ad30`（割込み）と `FUN_0027c4`（主ループ側）の間にエッジはありません。**割込みはフラグを
立てるだけで、消費側は別**という普通の作りです。初版はここを矢印でつないでいました。

## 2. 較正の消去は 1 セクタ、そのセクタは `0x30000-0x3FFFF` の 64 KiB 【確定】

デコンパイル結果そのもの:

```c
// FUN_002212 — サービス 0x07、サブ機能 0x06（消去）
FUN_00137e();
if      (LAB_0006a6_1 == 1) FUN_000ffe(1);
else if (LAB_0006a6_1 == 2) FUN_000ffe(0);

// FUN_000ffe
if (param_1 == 0 && LAB_0006a6_1 == 2) { … FUN_000ad6(buf, 0x2000, 3, 4); … FUN_0014b4(0x28c, 0, 1); }
if (param_1 == 1 && LAB_0006a6_1 == 1) { … FUN_000ad6(buf, 0xDFF0, 0, 4); … FUN_0014b4(0x270, 0, 7); }
```

**どちらが較正かは、隣に書いてある番地が決めます。** `FUN_000ad6(buf, lo, hi, len)` は
`FUN_002212` の書込分岐で `FUN_000ad6(buf, DAT_00e012, DAT_00e014, DAT_00e063)` と呼ばれており、
第 2・第 3 引数が下位 16bit と上位バイトです。したがって:

| 領域 | 検査番地 | 物理 | セクタ数 | 何か |
|---|---|---|---|---|
| **2** | `0x2000`, seg `3` | **0x32000** | **1** (`0x28c`) | **較正**。0x32000 は較正窓の先頭 |
| 1 | `0xDFF0`, seg `0` | 0x00DFF0 | 7 (`0x270`) | プログラム側 |

### 2.1 セクタ表は素の物理番地にあった 【確定】

初版は「記述子は実行時に RAM で組み立てられるので静的には読めない」と書きました。**これも誤りでした。**
`0x28c` を DPP0=0x0C 経由で読んで `01 01 00 00` というゴミが出たので、そう結論づけたのです。
実際は `FUN_0014b4` の `& 0x3fff` は**マスクであってページ選択ではなく**、`0x270` / `0x28c` は
**そのままの物理番地**です。

```
0x00270  00 80 00 00  00 00 01 00  00 00 02 00  00 00 04 00      ← プログラム 7 個
0x00280  00 00 05 00  00 00 06 00  00 00 07 00 |10 20 03 00      ← 最後の 4B が較正 1 個
```

各エントリは `lo:u16, hi:u16`（テレグラムと同じ分け方）:

| 表 | エントリ |
|---|---|
| プログラム `0x270` ×7 | `0x08000` `0x10000` `0x20000` `0x40000` `0x50000` `0x60000` `0x70000` |
| **較正 `0x28c` ×1** | **`0x32010`** |

### 2.2 なぜこの読み方が信じられるか —— BMW 自身のファイルと二重に一致

エントリは「消すセクタ**の中の**番地」です（だからテレグラムに長さが要らない）。導かれる区分:

| セクタ | 大きさ | 役割 |
|---|---|---|
| `0x00000-0x07FFF` | 32 KiB | **BOOT。どちらの表にも無い＝消されない** |
| `0x08000-0x0FFFF` | 32 KiB | プログラム |
| `0x10000-0x1FFFF` | 64 KiB | プログラム |
| `0x20000-0x2FFFF` | 64 KiB | プログラム |
| **`0x30000-0x3FFFF`** | **64 KiB** | **較正** |
| `0x40000-0x7FFFF` | 64 KiB ×4 | プログラム |

**合計ちょうど 512 KiB。** そして本プロジェクトが選んでいない二つの数字と一致します:

- 7 個のプログラムセクタは `0x08000` から始まり、BMW の `7843260K.0PA` も **`0x08000`** から
- 較正エントリは **`0x32010`**、BMW の `Y7843259.0DA` も **`0x32010`** から

BOOT が消去対象外なのも筋が通ります —— **消去を実行するコード自身がそこ（`0x017F0`）にある**からです。

`packages/ds2-smg2-write/src/sectors.ts` が実イメージからこれを読み、テストで固定しています。

### 2.3 残る整合しない点 【未解決・正直に】

§3 の通り、ドライバは `0x306B2` へ写されてそこで実行されます。`0x306B2` は**上の表では較正セクタの
中**で、消そうとしているセクタから実行することはできません。読み方は二つあり、決めていません:

1. `0x30000-0x3200F` は**フラッシュに重ねられた RAM** —— §5.2 が「用途不明」とし、0x00 が 83.2%
   （消去済みフラッシュなら 0xFF のはず）で、CRC 保護対象外なのは全部これで説明がつきます 【強い推定】
2. コピー先を DPP0=0x0C 経由で `0x306B2` と読んだ私の解釈が誤り

**どちらでも実務上の結論は同じ**です: `0x32010` 以降の較正は確実に消え、その手前の 8,416 バイトは
（フラッシュであれ RAM であれ）フルイメージに入っているので書き戻せます。

## 3. フラッシュアルゴリズムはコピーして実行される 【確定】

フラッシュを実行しながら同じフラッシュは消せないので、ルーチンを別の場所へ写して跳びます。

```c
// FUN_00097e
for (…) *(0x6b2 + i)  = *(0x17f0 + i);   // 0x017F0-0x0193A → 0x6B2
for (…) *(0x810 + i)  = *(0x193a + i);   // 0x0193A-…       → 0x810
FUN_0306b2();                             // 写した先を実行
for (…) *(0x810 + i) = 0;                 // 使用後は 0 で消す
for (…) *(0x6b2 + i) = 0;
```

`0x6b2` は DPP0=0x0C 経由で物理 **0x306B2**、`0x810` は **0x30810**。

**コピー元は `0x017F0`、コピー先が `0x306B2` です。** 初版はこれを逆に書いていました。

**`0x306B2` は書き込める領域である**（コードがそこへ書いてから跳ぶので）—— したがって §5.2 が
「用途不明」としている `0x30000-0x3200F` は少なくとも一部が RAM です 【強い推定】。
ダンプ時点でそこにあるのは ASCII `"0549T051…"` と 0x00 が 83.2% で、**命令ではありません**。
掃引の初期に「較正窓の真ん中で 971 命令の関数が出た」と警告が出たのは**正しい誤検出**でした
（0x00 の連続は `ADD R0, R0` として復号されるため）。初版はこれを「誤検出ではなかった」と
書きましたが、誤りです。

### 3.1 コピー元 `0x017F0` の中身 【確定】

```
017F6  MOV   R3, #5554h        アドレス定数 1
017FA  MOV   R4, #0010h        そのページ
017FE  MOV   R10, #AAAAh       アドレス定数 2
01802  MOV   R11, #0010h       そのページ
01806  MOV   R12, E000h        ← FUN_000af8 が置いた対象番地（下位）
0180A  MOV   R13, E002h        ←                     （上位/ページ）
0181A  MOV   R1, #2222h
0181E  EXTP  R11, #1 / MOV [R10], R1     定数 0x2222 を書く
01822  MOV   R2, #8888h
01826  EXTP  R4, #1  / MOV [R3], R2      定数 0x8888 を書く
0182A  ── E01E-E021 のマジック検査（'S' or 'e' / 0xAC or 0x96 / 0xCA / '5'）──
01892  MOV   R2, #00A0h
01896  EXTP  R13, #1 / MOV [R12], R2     コマンド 0xA0 を対象番地へ
0189A  MOV   R8, WDT / MOV R1, WDT / SUB R1, R8 / CMP R1, #007Dh   ← 0x7D tick のタイムアウト
```

固定番地への定数書き込みで解錠し、対象番地にコマンドバイトを書く形です。`0xA0` と
`0xAAAA`/`0x5554` という番地の並びは AMD/JEDEC 系のコマンドセットと整合します 【推定】——
ただし解錠データが `0x2222`/`0x8888` で JEDEC 標準の `0xAA`/`0x55` ではないので、
**「JEDEC 系である」と断定はしません**。`0xA0` はプログラム（書込）コマンドで、
**消去コマンド（0x30 / 0x10）はこの範囲にはまだ見つけていません**。

## 4. テレグラムの番地の並び 【ECU 側から独立に確認】

`docs/smg2-write-protocol.md` は BESTDIS の索引対から「番地はビッグエンディアン MSB 先頭」と
読みました。ECU 側のコードが同じことを言っています:

```c
DAT_00e012 = CONCAT11(DAT_00e061, DAT_00e062);   // 下位 16bit = e061:e062
DAT_00e014 = (ushort)DAT_00e060;                  // 上位バイト = e060
DAT_00e016 = (ushort)DAT_00e063;                  // e063 は長さ
```

テレグラム `32 09 07 06 A2 A1 A0 LL` に対し受信バッファは `e05C=32, e05D=09, e05E=07, e05F=06,
e060=A2, e061=A1, e062=A0, e063=LL`。したがって **番地はオフセット 4,5,6 に MSB 先頭**で、
`eraseTelegram(0x320E0)` が出す `32 09 07 06 03 20 E0 00` は正しい並びです。
**二つの独立な経路（BMW の SGBD と ECU のコード）が一致しました。**

**訂正:** 8 バイト目 `e063` は**長さフィールド**です。`docs/smg2-write-protocol.md` の初版は
「消去テレグラムは長さを持たない」と書きましたが、正しくは**フィールドは在り、消去では 0**です
（`FUN_002212` は `DAT_00e063 < 0x78` で全体を門番しています）。消去範囲を指定しないという
結論は変わりません。

## 5. まだ車が要るもの

**較正セクタの大きさは、もう車を必要としません**（§2.2 で解決）。残りはこれだけです:

| 事項 | なぜ静的に決着しないか |
|---|---|
| §2.3 の整合しない点 | `0x30000-0x3200F` が RAM か否か。実車で `FLASH_LESEN` を 2 回撃って値が変わるかを見れば済む（**非破壊**） |
| 消去コマンドそのもの | `0xA0`（書込）は見つけたが消去コマンドは未発見。`0x0193A` 以降の第 2 ブロックが候補（車不要、読解のみ） |
| フラッシュチップの型番 | イメージからは出ない。番地パターンからの推測はするが、断定しない |
| 鍵導出が MSS54 と同じか | `FUN_001c2a` の計算は読めたが、一致は実際に交換して確認する（W2） |

## 6. 初版の誤りと、それがどう見つかったか

| # | 初版の記述 | 実際 | 見つけ方 |
|---|---|---|---|
| 1 | 「1 セクタが `0x32000–0x37FFF` を覆う」 | **範囲の根拠なし** | 同じ文書の §2 が「境界は RAM を見るまで不明」と書いており、自己矛盾していた |
| 2 | 「領域 2 → `FUN_000ffe(1)`、領域 1 → `FUN_000ffe(0)`」 | **逆**。1→(1), 2→(0) | デコンパイル結果を読み直した |
| 3 | 「`0x306B2` は RAM 常駐コードの**コピー元**」「971 命令は誤検出ではなかった」 | **コピー先**。元は `0x017F0`。971 命令は**正しく誤検出** | `0x306B2` のバイトを見たら ASCII `"0549T051"` だった |
| 4 | `FUN_00ad30 → FUN_001c2a → FUN_002212` の連鎖 | エッジ**なし**。両方を呼ぶのは `FUN_0027c4` | 掃引のエッジを問い合わせた |
| 5 | （二版）「セクタ記述子は実行時に RAM で組み立てられるので静的には読めない」 | **読める**。`0x270`/`0x28c` は素の物理番地 | DPP 経由で読んでゴミが出たとき、「読めない」ではなく**「読み方が違う」**を先に疑うべきだった。マスクとページ選択を取り違えていた |

**5 の教訓**: 一度の失敗した読み出しから「原理的に不可能」を結論した。ゴミが出たのは
**手法の誤りの症状**であって、対象の性質ではなかった。`& 0x3fff` を見て「ページ相対だ」と
決めつけ、`& 0x3fff` が単に上位ビットを落とすマスクである可能性を考えなかった。

**副産物としてデコーダのバグが 2 件見つかりました**（`packages/c166`）:

- `EXT` のレジスタ形式（`0xDC`）で、セレクタをビット 3、レジスタを 3 ビットとして読んでいた。
  正しくは `<irang2:2><restore:1><seg:1><reg:4>`。`dc 0b` を `EXTS R3` と誤読していたが、
  正しくは `EXTP R11` —— **R11 は 3 ビットでは表せない**。フラッシュドライバが
  `R10 = #AAAAh` / `R11 = #0010h` と番地とページを対で置いていたので気づいた。
- `EXT` が有効なのにページがレジスタ由来で不明なとき、**DPP にフォールバックして番地を出していた**。
  `EXTP Rwm` は「この命令に限り DPP を使うな」という意味なので、これは最も
  自信を持って間違える経路だった。今は未解決として返す。
