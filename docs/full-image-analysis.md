## 2. MCU とメモリマップ

### 2.1 コア

**C16x / ST10 派生であることは確定**（`0x00000` = `FA 00 4E 04` = JMPS 00:044E、以下 128 本の 4B JMPS）。

**型番・ベンダは特定できない — 推定にも達しない。** ESFR の識別レジスタが全部ゼロを返す:

```
0x00F078 IDPROG  = 0x0000
0x00F07A IDMEM   = 0x0000
0x00F07C IDCHIP  = 0x0000
0x00F07E IDMANUF = 0x0000
```

Infineon の C167CR なら IDMANUF は 0x1820 を返す。イメージ全体に "C167" / "C166" / "ST10" / "Siemens" / "Infineon" の文字列も無い。SYSCON `0x00FF12 = 0x0204` は ROMEN=0 なので**内蔵 ROM は写像されていない**が、これは「ROM を無効化した」とも「ROM レス品」とも読める。ST10R167 のようなロムレス品でも観測は全部一致する。「C167CR クラス」と書きたくなるが、**書けない**。

### 2.2 ベクタテーブルは 2 段 — これが確定した

| | ハードウェア表 `0x00000-0x001FF` | 第2表 `0x10000-0x101FF` |
|---|---|---|
| エントリ | 128 × 4B JMPS | 128 × 4B JMPS |
| seg0 直行 | **5 本** — `0x00→0x0044E`, `0x08→0x02BCE`, `0x10→0x02BDA`, `0x18→0x02BE6`, `0x28→0x02BF2` | — |
| 第2表への転送 | **123 本** (`FA 01 <同一オフセット>`) | — |
| 自己ジャンプ (無限ループ) | — | **109 本** |
| 実ハンドラ | — | **19 本** |

**確定。** 実測: L1 の seg0 直行 5、転送 123、L2 の self-loop 109 / live 19。

「規則的な間隔で `0x010004` / `0x01000C` / `0x010014` / `0x01001C` に飛ぶ」という以前の観察は解決した。あれは特殊な 4 つのターゲットではなく、**未使用ベクタ 0x04/0x0C/0x14/0x1C の転送スロットで、中身が自分自身への JMPS**（`FA 01 04 00` = JMPS 01:0004 = 自分）。C166 の定番「未使用割込みはハングさせてウォッチドッグにリセットさせる」イディオム。

生きている 19 本 (vector offset → handler):

```
0x000→0x010200  0x008→0x011206  0x010→0x011236  0x018→0x011266  0x028→0x011296
0x050→0x018702  0x088→0x018A1A  0x08C→0x009478  0x0A0→0x010608  0x0A8→0x00ACF0
0x0AC→0x00AD30  0x0B0→0x00B0B4  0x0B4→0x010834  0x0B8→0x010836  0x0BC→0x0107FE
0x0C8→0x010E92  0x0DC→0x01AF2C  0x104→0x010954  0x11C→0x0112C6
```

ハンドラ同定で**確定**しているのは ASC0 系だけ:
- `0x00AD30` — `MOVB R8, FEB2h` @ `0x00AD3A` = S0RBUF 読み出し = 受信割込み
- `0x00B0B4` / `0x00ACF0` — bitoff 0xD8 (S0CON) に BFLDH で bit 8-10 クリア、S0RBUF を 2 回ダミーリード、S0TIC/S0RIC/S0EIC をクリア・再許可 = 送信/エラー割込み

`0x009478` を「周期タイマ」と読むのは**推定**に留める。オペランド `0x024A` は DPP0=0x000C 経由だとフラッシュ `0x3024A`（つまり読み出し定数）に落ちるので、「外部 RAM のカウンタをインクリメント」は成立しない。T2IC/T3IC/S0TIC/S0RIC への書き込みはある。

**実務上の帰結:** 割込みハンドラを差し替えるなら編集するのは `0x010000-0x0101FF`。`0x00000-0x001FF` は不変として扱ってよい。

### 2.3 クロック — fCPU = 16.000 MHz 【強い推定】

二つの独立な経路が同じ値を出す。

**(a) ASC0 ボーレート発生器**

| 書き込み位置 | S0BG | 対になる S0CON | 意味 |
|---|---|---|---|
| `0x001BBA`, `0x00AF90`, `0x00B150`, `0x00B1D4` | `#0033h` (51) | `#80F7h` @ `0x001BBE`, `0x00AF94`, `0x00B154`, `0x00B1D8` | S0M=7, S0PEN, S0ODD=0 → **8E1** = DS2 |
| `0x00B434` | `#002Fh` (47) | `#80D1h` @ `0x00B438` | S0M=1, S0PEN=0 → **8N1** = KWP2000 |

S0BRS (bit 12) はどちらもクリア。`baud = fCPU / (32·(S0BG+1))` より 9600 baud には fCPU = 32·52·9600 = **15,974,400 Hz**。0x002F 側は 32·48 → 10,416.7 baud = KWP2000 の 10400。**DS2 と KWP2000 の 2 本の線形式が同じ fCPU で同時に満たされる**のがこの論証の芯。

**(b) オンチップ CAN ビットタイミング** `0x00EF04 = 0x49C0` → BRP=0, SJW=3, TSEG1=9, TSEG2=4 → 1+10+5 = 16 tq/bit, tq = 2/fCPU → **bit rate = fCPU/32**。16.000 MHz ちょうどで 500,000 bit/s = E46 パワートレイン CAN。この時 UART は 9615.4 baud (+0.16%、余裕で許容内)。

CAN が実際に動いていた証拠: `0x00EF00 = 0x0A` (INIT クリア), `0x00EF01 = 0x18` (TXOK, RXOK セット)。設定の残骸ではない。

**未説明:** `0x01079A` に第三の定数 `S0BG = #001Fh` (16 MHz なら 15,625 baud)。用途不明。

### 2.4 SFR 窓は生きている 【確定】

`0x00FE00-0x00FFFF` は実行中のレジスタファイルが読めている:

| | 値 | 備考 |
|---|---|---|
| S0CON `0x00FFB0` | `0x80E7` | 8E1。**S0REN (bit 4) はクリア** — 書き込み定数 0x80F7 では立っているので、ダンプ時点で受信器が止まっていた。K-line 半二重のターンアラウンド中と整合 |
| SSCCON `0x00FFB2` | `0xC007` | SSC 有効・マスタ・8bit。隣接レジスタの同定が正しいことの裏付け |
| SYSCON `0x00FF12` | `0x0204` | ROMEN=0 |
| DPP0-3 `0x00FE00` | `03 00 0d 00 0b 00 03 00` | DPP0=3, DPP1=0x0D, DPP2=0x0B, DPP3=3 |

### 2.5 DPP について — 単一の写像式は成立しない 【重要な否定結果】

「DPP0=0x0C だから、キャリブレーション項目のイメージオフセット A は 16bit 定数 (A − 0x30000) で参照される」という読み方は**採らないこと**。

- ライブ SFR は **DPP0 = 0x0003**。0x0C ではない。
- DPP0 は `PUSH DPP0` / `MOV DPP0,#000Ch` / `POP DPP0` で保存復元される呼び出し側保存レジスタ。`EC 00` (PUSH DPP0) が 18 箇所、`MOV DPP0,#000Ch` 24 箇所のうち 13 箇所はその直後。
- 初期化ブロック内ですら `MOV DPP0,#000Bh` が `0x010228` と `0x0102F6` にある。
- `EXTP #000Ch,#1` (`D7 40 0C 00`) が明示的に置かれている箇所が複数あるが、EXTP は「常駐 DPP がそのページを指していない」から出るもの。

成立するのは **「`MOV DPP0,#000Ch` を実行した直後の領域に限り、16bit アドレス 0x0000-0x3FFF は物理 (オフセット − 0x30000)」** という局所的な形だけ 【推定】。DPP1=0x000D と DPP2=0x000B は初期化書き込み (`0x000458`, `0x00045C`, `0x010204`, `0x010208`) とライブ値が一致するので、こちらは 【強い推定】。

## 3. チェックサム — 解けた。ただし探索空間の大きさは正直に書く

### 3.1 結論

**アルゴリズム:** ビット単位 reflected CRC-16、多項式 `0xA001`、xorout なし、終端アドレス **inclusive**、複数ブロックはテーブル順に連結してアキュムレータを持ち越す。**記述子ごとに異なるのは seed だけ。**

**記述子形式** `{u16 checksum, u16 blockCount, blockCount × (u32 start, u32 end)}` — 全部リトルエンディアン。

### 3.2 三つの記述子 — 全部再現した 【確定】

| 記述子 | 格納値 | n | 範囲 | バイト数 | seed | seed の出所 |
|---|---|---|---|---|---|---|
| `0x03C24` (boot) | `0x6858` | 1 | `0x00000-0x02C29` | 11,306 | `0x2D2D` | `0x03FE6`、`0x00B4C` の `MOV R2,[0x3FE6]` / `MOV [0x0696],R2` が直接ロード |
| `0x0C136` (program) | `0x2660` | 9 | 下表 | 269,090 | `0x7878` | far ポインタ `0x0C02A` → `0x0000C0EE` |
| `0x32080` (calibration) | `0x4C83` | 1 | `0x320E0-0x378BF` | 22,496 | `0x7878` | far ポインタ `0x0C04A` → `0x0003201C` |

program の 9 ブロック:
`0x08000-0x0BCBD`, `0x0C000-0x0C05D`, `0x0C21E-0x0C32E`, `0x10000-0x1CC8F`, `0x2C000-0x2F998`, `0x40000-0x4F5DD`, `0x50000-0x5FB8F`, `0x6D000-0x6F573`, `0x70000-0x7BFE9`

再現コマンド（そのまま動く）:

```python
def crc(b, init):
    c = init
    for d in b:
        c ^= d
        for _ in range(8):
            c = (c >> 1) ^ 0xA001 if c & 1 else c >> 1
    return c
# 0x4C83
crc(D[0x320E0:0x378C0], 0x7878)
```

24 KiB 窓ファイル `f6de6103584b.bin` でも同じ (オフセット `0x0E0`-`0x58BF`) で `0x4C83`。

### 3.3 コードの実体 【確定】

| 位置 | 内容 |
|---|---|
| `0x00D10` | `0x0C04A` / `0x0C04C` から far ポインタを読み、seed を low-byte→high-byte で RAM `0x0698` に組み立てる |
| `0x00DAE` | 変位 `0x2084` / `0x2086` で START を読む |
| `0x00D6E` | 変位 `0x2088` / `0x208A` で END を読む |
| `0x00D84` | カーソルを R12:R13、`&acc` (`#0x0698`) を R14 に渡して `CALLS 0x00:0x0DEE` |
| `0x00DEE-0x00E1F` | バイト処理。`SHR R4,#1` (`7C 14`) @ `0x00E02`/`0x00E0E`、`XOR R4,#0xA001` (`56 F4 01 A0`) @ `0x00E04`、ループ境界 `CMP R15,#8` (`46 FF 08 00`) @ `0x00E16` |
| `0x00DC4` | acc を `0x0698` から読み、`CMP R4,[0x2080]` で格納値と比較 |
| `0x1228A`/`0x1228C` | `MOVB RL5,[0x2082]` でブロック数を読み CMPB/JMPR ループ。ペアは stride 8 で `MOV R10,[R4+0x2084]` 等 |
| `0x08002-0x08201` | 256 エントリ ARC ルックアップ表 (LE u16)。イメージ中に **1 回だけ** 出現。BE 版・0x8408 版は不在 |

### 3.4 探索空間 — なぜ 6,048 通りが外れたのか、正直に

事前に試した 6,048 通り (sum8/sum16le/sum16be/xor16le/xor8/neg_sum8 + CRC16 10 種 × 189 範囲) には **CRC-16/ARC も MODBUS も入っていた**。外れた理由は範囲でも多項式でもなく、**init を 0x0000 / 0xFFFF に固定していたこと**。

ここは論理的にきちんと言っておく必要がある。

- CRC は init について GF(2) 上アフィンなので、**メッセージと多項式を固定すれば init → crc は全単射**。つまり「正しい範囲さえ分かれば、65,536 個の init のうち必ず 1 個が格納値に一致する」。**単独の記述子で ARC が合ったこと自体には情報量がゼロ。**
- 32,768 個の奇数多項式のどれを選んでも、それぞれ固有の init で必ず合う。

したがって identification の重みは以下の 3 点にしかない:

1. **互いに素な 3 データセット** (11,306 B / 269,090 B / 22,496 B、重複なし) が**同一の多項式**で解け、うち 2 つが**同一の seed 0x7878** を要求する。boot だけ 0x2D2D。この非対称は偶然では出ない。
2. seed 2 個が、ポインタ表 (`0x0C02A`, `0x0C04A`) とコード (`0x00B4C`) が**独立に指定しているフラッシュアドレス**に実在する。
3. reflected 0xA001 の 256 エントリ表がイメージ内 `0x08002` に実在し、その表を読むテーブル駆動カーネルが `0x122D0-0x122F7` にある。

**なお `0x7878` は ASCII `"xx"`、`0x2D2D` は `"--"`。** `0x32010-0x3201E` は 'x' の連続なので「`0x3201C` が特別」なのではなく、far ポインタがたまたまそこを指している。**別ソフトウェアレベルのイメージでは seed が変わりうる** — 現状 1 イメージでしか検証していない。この一点だけ 【強い推定】。範囲・多項式・記述子形式は 【確定】。

### 3.5 保護される範囲・されない範囲 【確定】

```
0x32080-0x320DF  無保護  ← checksum語・blockCount・範囲レコード自身
0x320A0-0x320DF  全 0xFF (64 B、実測)
0x320E0          保護開始。第1バイトは 5A5A マジック (イメージ中 5A5A は 1 回のみ)
0x378BF          保護終端 (inclusive)。ここが連続データの最終バイト
0x378C0-0x37FBF  全 0xFF (1,792 B、実測)  無保護
0x37FC0-0x37FF3  IDENT0 の実データ 52 B    無保護
```

512K XDF の**ユニークアドレス 134 個のうち 132 個が保護範囲内**。範囲外は 2 個だけ:

- `0x32080` — チェックサム語そのもの
- `0x37FC0` — IDENT0

つまり **XDF 定義テーブルを 1 個でも編集したら必ず CRC 再計算が要る。IDENT0 を書き換えても CRC は変わらない。**

フルリフラッシュ (キャリブレーションだけでなくプログラム領域) をやるなら `0x0C136` の `0x2660` も直す必要がある。

なお `0x2660` と `0x4C83` は AIF / プログラミングログの各レコードに**隣接ペアで記録**されている (`0x0400E` と `0x04010` から始まり、`0x03F64-0x07BBF` を約 `0x14C` 間隔で反復)。プログラミング時点のチェックサムを ECU 自身が控えている。

## 4. 識別ブロック / バージョンブロック、そしてより良いプローブアンカー

### 4.1 ZB ブロック — 5 回ではなく 6 回 【確定】

```
0x2FF70  '0549T0510510' × 3        36 B
0x2FF94  '7843260'     × 6        42 B   ← ZB
0x2FFBE  '--+'                      3 B
0x2FFC0  ブロック末尾。0x2FFC1 以降 0xFF
```

実測: `D.count(b'7843260') == 6`、出現位置 `0x2FF94, 0x2FF9B, 0x2FFA2, 0x2FFA9, 0x2FFB0, 0x2FFB7`。ブリーフの「5 回」は文字列ダンプの数え間違い。**`packages/ds2-smg2/src/layout.ts` は既に ×6 と書いてある** ので、直すべきはブリーフ側であってコード側ではない。`0x2FFC0` は `0x28000-0x2FFFF` バンクの最終非-0xFF バイト。

### 4.2 保護範囲との関係 — 直感に反する 【確定】

| ブロック | 内容 | 保護範囲内か |
|---|---|---|
| `0x37680` | `ALLGEMEIN: VERSION_510_VON__GETRAG__FUER_E46_VOM_-15.04.09/13:55` | **内** |
| `0x37700` | `GETRAG DATEN: ZB_622.0.0252.00-HW_622.0.0248.00-…` (XDF の IDENT1) | **内** |
| `0x37770` | `MMS DATEN: PR_003948008007-DT_003948009007-15.06.04/11:23` | **内** |
| `0x37FC0` | `0549T05105100570` × 3 (XDF の IDENT0) | **外** |
| `0x2FF70` | ZB ブロック | 外 (そもそも別バンク) |

「識別文字列は全部チェックサム範囲外」という一般則は**成立しない**。3 つが範囲内にある。範囲外なのは IDENT0 と ZB ブロックだけ。

### 4.3 XDF の IDENT1 は頭が 21 バイト切れている 【確定】

XDF: `mmedaddress="0x37715" mmedcolcount="60"`
実体: `0x37700-0x37754` が 85 印字可能バイト、`0x37755` が NUL。正しくは **開始 `0x37700`、長さ 86 B**。切り落とされているのは先頭の `GETRAG DATEN: ZB_622.` (21 B) と末尾の `---+` (4 B)。`0x376F0-0x376FF` は 0xFF なので開始位置に曖昧さは無い。

（これは `docs/undefined-tables.md` §4 に既出。この解析で追加されたのは NUL 終端と正確な印字可能長の内訳だけ。）

### 4.4 プローブアンカー — 何を使うべきか

現状の probe は `0x37715` と `0x37FC0` しか見ない。この 2 つは **ZB 番号を含まない** ので、`scoreCandidate` が `digitsOf(...).includes(expectedZbNumber)` という決定的分岐に到達できず、正解候補が 0.6 で頭打ちになり `STRONG_MATCH = 0.75` を超えない。

**アンカー候補を強い順に:**

| アンカー | 内容 | 一意性 | 評価 |
|---|---|---|---|
| `0x32080` 12 B | `83 4C 01 00 E0 20 03 00 BF 78 03 00` | 全 512 KiB で 1 回 | **確定に一意**。ただし `0x4C83` は**チューニングで変わる** — 書き込み後は不一致になるので、そのまま固定バイト比較に使ってはいけない |
| `0x320E0` の `5A5A` | 保護範囲の先頭マジック | `5A5A` は全画像で **1 回だけ** (実測) | **最良**。値がチューニングで変わらない。`0x32084/0x32088` のポインタを読んで `0x320E0` に `5A5A` が居るか、`0x378BF` の次から 0xFF が始まるかを見る自己参照検証ができる |
| `0x2FF90` / 56 B | ZB ブロック | ZB が 6 回繰り返す | `layout.ts` に既に定義済み。**ただし粗い**: 数字だけ比較すると開始アドレスが −45〜+39 ずれても一致する (85 通りの連続開始位置)。0x100000 級のずれは分離できるが細かいずれは分離できない |
| `0x08200` | `@@special $Revision:   1.5  $` / `sys_3 $Revision:   1.17  $` | 画像中 `$Revision` は 2 回のみ | ソフトウェアバージョンに対して安定しやすい唯一の候補。ただし別バージョンでの検証は未実施 |
| `0x37715` / `0x37FC0` | 現行アンカー | — | ZB を含まない。**これだけでは確定できない** |

**現実的な設計:** `0x320E0` の `5A5A` + `0x32084`/`0x32088` のポインタ往復を第一アンカー、`0x2FF90` の ZB を第二アンカーにする。この 2 つが揃えばアドレス空間は確定と言ってよい 【強い推定】。ただし「均一オフセットずれ」以外の写像モデル (セグメント分割の違い等) に対する耐性は検証していない。

なお、**DS2 の 0x53 (製造データ) はこの車では応答しなかった** — 両セッションのログが `manufacturer data read answered DS2 status 0xb0`。`FEP 7843260 SIEMENS 2F` という文字列は `src/lib/practiceEcu.ts:102-106` のシミュレータが生成したもので、実測値ではない。ただし**これはプローブが確定できなかった原因ではない**: `expectedZbNumber` はオペレータがテキスト欄に入力する値 (`src/app/page.tsx:167` → `useSmg2Link.ts:311`) で、0x53 の応答は表示用に hex 整形されるだけ。0x53 が完璧に応答していても分岐は発火しなかった。原因はアンカーの位置。

## 6. キャリブレーション相互参照と未定義テーブルへの決着

### 6.1 XDF が丸ごと落としている 11 番目の AUTO テーブル 【確定】

AUTO 系は **stride `0x160` の 11 連続ブロック** (`0x35A00`-`0x3691F`)。XDF は 10 個しか定義せず、**7 番目の位置を飛ばしている**。

XDF が宣言している x 軸アドレス:
```
0x35A00 (A1)  0x35B60 (A2)  0x35CC0 (A3)  0x35E20 (A4)  0x35F80 (A5)  0x360E0 (FGR)
   ↓ ここで 0x2C0 = 2×0x160 のジャンプ
0x363A0 (MODE7)  0x36500 (MODE8)  0x36660 (MODE9)  0x367C0 (WARMUP)
```

飛ばされたアドレス `0x36240` の中身（実測）:

- x 軸 `0x36240-0x3625F`: `0, 7, 12, 25, 50, 75, 100, 112, 125, 150, 162, 175, 200, 225, 250, 252` — 他の 10 本と同型
- z `0x36260-0x3639F`: 10 行 × 16 u16、各行先頭 `496 / 832 / 1232 / 1712 / 2080 / 224 / 576 / 816 / 1392 / 1376`
- **`0x36240-0x3639F` 全 352 B に 0xFF が 1 バイトも無い** (実測 FFcount = 0)

境界が両側から釘付けになっている:
- FGR の z ブロックは `0x36100 + 320 = 0x36240` でちょうど終わる
- 系列は `0x367C0 + 0x160 = 0x36920` で終わり、そこが XDF の次の系列 (`AUTO: A1 Speed Thresholds, Braking`) の開始位置

11 本の x 軸のうち 9 本はバイト単位で同一。異なるのは `0x36240` と `0x367C0` (WARMUP) の 2 本で、この 2 本は同じ変種軸 (162 が挿入され 242 が落ちている) を共有する。**欠落ブロックは WARMUP の兄弟** 【推定】。

**インパクト:** 352 B の生きたシフト速度キャリブレーションが TunerPro に一切表示されず、しかもチェックサム再計算付きライタは「編集されなかった」として黙って保存する。チューナーはその存在を知らないまま。

追加すべき定義: x = `0x36240` (16 要素, X*.4)、z = `0x36260` (16×10, X/16)。

### 6.2 `0x350D4` を「X/16 = km/h」と書くのは誤り 【強い推定】

ECU の X/16 系テーブルは**例外なく 16 で割り切れる**。実測:

| | テーブル数 | 値の数 | 16 で割り切れる |
|---|---|---|---|
| XDF の `X/16` z 軸すべて | 34 | 2,227 | **2,227 (100.00%)** |
| `0x350D4-0x353D4` | — | 384 | **34 (8.9%)** |

ランダムな u16 なら 6.25% なので、8.9% はほぼ偶然水準。代わりに **10 の倍数が 219 個 (57.0%)**、先頭 6×16 ブロックでは 96 個中 72 個 (75.0%)。第 1 行の実測値:

```
900 910 920 940 980 1080 1130 1170 1210 1250 1290 1330 1617 1617 1617 1617
```

10 の倍数でない 165 個のうち、`1617/1717/1817/1917` (ちょうど 100 刻み) が 72 個、`1224/1241/1258/1275/1292/1309/1326/1343` (17 刻み) が 48 個を占める。

（100.00% を割っている 34 本以外に X/16 と書かれた x 軸が 6 本あるが、これらは `0, -10, -25, -45, -60, -80, -100, -120` という**符号付き減速軸**で、別単位。u16 として数えると割り切れないので混ぜないこと。）

**結論: `0x350D4` のジオメトリを XDF に定義するのは安全。スケーリングを X/16 km/h と書くのは危険。** そう書くとチューナーには 56-120 km/h と表示されるが、計測上それは別の単位。

### 6.3 `0x372FC` "CFG: Logic" は XDF の欠陥ではない 【確定】

以前「定義が消去済みフラッシュを指している」と確定扱いにしたが、**両方の解釈が誤り**。

1. XDF 自身の `<description>` に `Default: 11111111  11111111` と書いてあり、続いて 7 行のビット凡例がある (0000001 = 横 G + スロットル差分ロジック、0000010 = 横 G、0000100 = ゼロスロットル/FGR、0001000 = 前後 G、0010000 = 18 km/h 未満ギア 1 徐行、0100000 = FGR ギア 6、1000000 = アップシフト保留)。**0xFFFF = 全オプション有効 = 文書化されたデフォルト。**
2. `0x372FC` を含む 0xFF の連続はわずか **3 バイト** (`0x372FB` は `0x372FA` の s16 `-2` の上位バイト、`0x372FC`, `0x372FD`)。フラッシュ消去はセクタ単位で来る。密なデータ中の 3 バイトの穴は消去ではない。
3. 周辺のアラインメントが正しいことの証明: `0x372F0` からの s16 は `12, -8, -6, 7, 5, -2, -1`。直後 `0x37304` の `0xAA` は XDF の `CFG: Lever Plus/Minus` (文書化されたデフォルト `AAh`)、`0x37306` の u16 `0x1194 = 4500` は `CLUTCH: Overload Cooldown time`。
4. XDF 全体で完全に 0xFF なのは `0x372FC` だけ。他の 132 バイトの XDF 被覆 0xFF は全部 `mmedtypeflags 0x03` (符号付き) 軸の負値の上位バイト (例: x 軸 `0x36920` = `0, -10, -25, -45, -60, -80, -100, -120`)。

**唯一の実際の問題は表示上のもの:** `mmedtypeflags 0x02` なのでビットフィールドではなく `65535` として表示される。

**ツールへの警告:** 「全 0xFF の定義」を警告するロジックを入れると、ここで偽陽性を出す。

### 6.4 XDF 被覆の実測

| | バイト数 |
|---|---|
| 512K XDF の `<EMBEDDEDDATA>` 総数 | 221 (うち `mmedaddress` 付き 145、ユニークアドレス 134) |
| 被覆バイト (和集合) | **5,477** (`0x32080`-`0x37FEF`) |
| 保護範囲 `0x320E0-0x378BF` | 22,496 B、うちプログラム済 (非 0xFF) **12,187** |
| そのうち XDF 被覆 | 5,427 |
| **プログラム済かつ未定義** | **6,894 B (56.6%)** |
| 24 KiB 窓全体 | 24,576 B、プログラム済 12,351、被覆 5,477 (22.3%) |

24K XDF は 512K XDF と**同一の 5,477 B 集合**に展開される。定義がどこか別の場所にあるわけではない。

「6,894 B が生きたキャリブレーション」とまでは言えない — うち 1,636 B は `0x00`、194 B は `0x37680-0x377FF` の GETRAG/MMS バージョン文字列 (ドキュメントであってチューナブルではない)。それでも大半は数値配列。

### 一行でまとめると

**チェックサムは解けた** — reflected CRC-16 (0xA001), seed 0x7878, 範囲 `0x320E0-0x378BF` inclusive、範囲は ECU 自身が `0x32082` 以降に持っている。6,048 通りが外れたのは範囲でも多項式でもなく init を 0/0xFFFF に固定していたから。**これでツールは書いてから正しいチェックサムを再生成できる。** それ以外の最大の実務的発見は、XDF が 352 B の生きたシフト速度テーブル (`0x36240`) を丸ごと落としていること、`0x350D4` を km/h と読むのが間違いであること、そして `0x372FC` は欠陥ではなかったこと。MCU の型番は、このイメージからは出ない。
